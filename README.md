# Dispute Autopilot

*A three-stage chargeback loss-prevention system for Razorpay merchants — predict chargeback risk, preserve evidence at transaction time, and decide contest-vs-accept on expected value, with published precision, recall, and calibration on a held-out temporal split.*

Razorpay AI Buildathon, Track 02 — AI Risk Manager. Author: Ali Ansari.

> **This system is defense-only.** It scores disputes and drafts grounded chargeback responses. It cannot generate, alter, or synthesise evidence for real use, and it refuses to contest — downgrading the decision to `REVIEW` — whenever the evidence it would need does not actually exist in the vault.

## What this is

Dispute Autopilot is a three-stage pipeline: predict, vault, respond. Stage 1 scores every transaction for P(chargeback) at collection time, using a LightGBM classifier trained on IEEE-CIS fraud-detection data and calibrated with isotonic regression. Stage 2 turns that score, multiplied by transaction amount, into an evidence-preservation posture — none, a passive snapshot (AVS/CVV result, device fingerprint, T&C acceptance), or an active one (plus signature-on-delivery and a customer-communication record) — because preserving evidence costs money and most transactions are never disputed. Stage 3 runs only when a real dispute arrives: it retrieves whatever was vaulted, gates on whether the reason code's required evidence fields are present, computes the expected value of contesting versus accepting, and — only if the answer is `CONTEST` — asks an LLM to draft a representment using nothing but vault contents, which a deterministic verifier then checks claim-by-claim before anything is allowed near the Razorpay API.

## Prior art

This project is not novel, and is not presented as novel.

| Prior art | What it covers |
|---|---|
| Stripe Smart Disputes | AI dispute handling inside a PSP |
| Chargeflow | Fully automated evidence collection, drafting, submission, tracking |
| Justt | Per-dispute dynamic argument construction, A/B tested |
| Midigator / Kount | Template-assisted representment |
| Verifi Order Insight (Visa), Ethoca Consumer Clarity (Mastercard) | Pre-dispute deflection by pushing order data to the issuer at network level; Visa CE 3.0 |
| US Patent 10,839,394 | Representment selection by expected value: `P*(A-F) - (1-P)*C` — the exact formulation Stage 3's decision rule follows |
| SSRN: "AI-Powered Chargeback Prediction and Dispute Automation Using Explainable Deep Learning Models" | The same problem, academically |

All four commercial products above and both deflection networks ship this capability today, at production scale, to real merchants. **The honest claim is narrower than novelty:** commercial vendors publish win rates, which are unfalsifiable from outside — nobody can check them against a labelled test set. None of them publish precision, recall, calibration, or false-positive cost. This project is the open, measurable version: public data, a published split protocol, and a confusion matrix denominated in rupees.

The differentiation that actually holds up: (1) published, reproducible held-out metrics — nobody in this space publishes a confusion matrix; (2) Razorpay-native, where incumbents integrate Stripe/Adyen/Braintree; (3) a groundedness verifier and a refusal gate — incumbents optimise win rate, none publish a hallucination rate or refuse to file, which is also the cleanest answer to "strictly defense-only"; (4) Indian market context, complementary to (not duplicating) Razorpay Thirdwatch, which covers RTO/COD rather than chargebacks.

Calibration *lowers* PR-AUC here (0.4405 → 0.4243). This is disclosed rather than hidden: isotonic regression is a step function and collapses continuous scores into a much smaller number of distinct levels, which costs average precision through tie structure — ranking quality is not degraded. Calibration is kept anyway, because every downstream decision in Stage 3 is an expected-value computation, and EV arithmetic run on uncalibrated scores is meaningless (per `eval/run_eval.py`, uncalibrated scores materially overstate P(chargeback) relative to the true base rate).

Baselines (flag nothing, flag everything, hand-written rules, the model) are reported together in Family B below, in rupees, because "better than baseline" is a policy question, not a detection-quality question on this data.

Model uplift vs. flag-everything: **+₹542,539**. Beating "flag everything" in rupees — not accuracy, not AUC — is the headline result, and it is a small margin relative to the size of the two numbers being subtracted.

**A finding that must be disclosed, not smoothed over:** the EV-optimal threshold is **0.001**, which sits on the boundary of the sweep range (`[0.001, 0.999]`, 100 steps), not in its interior. `eval/reports/metrics.json` flags this explicitly (`ev_optimal_threshold_is_at_sweep_boundary: true`). At that threshold, precision is 3.74% and recall is 99.4% — the EV-optimal *policy*, under these cost assumptions, is to vault evidence for nearly every transaction, because the posture cost (≤ ₹75) is cheap relative to the average exposure of a missed chargeback. This is a fact about the cost inputs, not a claim that the classifier cannot discriminate — Family A shows it can. Read Family B as "given these assumptions, spend on almost everyone," not as "the model recommends contesting almost everyone" — Stage 3's actual contest decision runs a separate rule (below), not this sweep threshold directly.

### Family C — Generation quality — **MEASURED**, synthetic evidence corpus

From `eval/reports/generation_metrics.json`, regenerated by `python -m eval.run_generation_eval`.
Model: `claude-sonnet-5 at effort=medium`. 20 API calls, 26,962 input and 9,939 output tokens, **USD 0.1533** — measured from `response.usage`, not estimated.

Stratified on **evidence favourability**, not vault posture. An earlier version of this harness
alternated ACTIVE/PASSIVE posture, which produced a corpus where "say nothing" was the correct
answer almost everywhere: two bundles carrying claims out of twenty cases, and a groundedness
figure averaged over empty bundles, which score 1.0 for free. It measured the harness, not the model.

| | Contestable (AVS match) | Adverse (AVS mismatch) |
|---|---|---|
| Cases | 10 | 10 |
| Bundles with attributed claims | 10 / 10 | 10 / 10 |
| Mean claims per bundle | 4.7 | 5.0 |
| **Groundedness** (over attributed bundles) | **1.0** | **1.0** |
| Ungrounded claims, 95% upper bound | 0.3 | 0.3 |
| Malformed responses | 0 | 0 |

A further 7 cases were refused by the completeness gate before any API call was made. That
refusal is deterministic and is **not** a model property, so it is reported separately and never
folded into the figures above.

**Read the upper bound, not the point estimate.** Zero ungrounded claims in ten attributed bundles
is consistent with a true ungrounded rate as high as **30%** (rule of three). The measurement is
real; the sample is small, and the bound is the honest summary of what it supports.

**What the adverse stratum actually measures, and a correction.** It was designed to measure
*refusal* — whether the assembler declines to argue a case the evidence does not support — and
earlier runs did show exactly that behaviour. Instructing the model that both `fields` and `claims`
must be non-empty removed it. The stratum now measures groundedness under pressure: adverse
evidence is where the temptation to spin is highest, and the assembler reported the AVS mismatch
faithfully rather than dressing it up. That is defensible, since assembly and the contest decision
are separate concerns, but it was a side effect of a prompt fix rather than a design choice, and
this README does not describe it as the plan.

**A gap this exposed.** Nothing in the decision path factors evidence *favourability* into the
contest choice. `w_completeness` measures whether required evidence is present, not whether it
helps. The system will contest on an AVS mismatch if the expected-value arithmetic says so. That is
a real limitation, found by measurement, and it is not fixed in this submission.

## The label, and why it matters

Per the competition host, IEEE-CIS `isFraud=1` means *a chargeback was reported on the card, plus transactions posterior to it linked by user account, email, or billing address*. If nothing is reported within 120 days, the transaction is labelled legitimate.

This has three consequences that shape the whole project:

- **Stage 1 is a chargeback predictor by construction**, not a fraud detector with a proxy label. The label *is* the event being predicted. This is a strength, and it is stated plainly rather than left implicit.
- **The dataset cannot distinguish first-party misuse (friendly fraud) from genuine third-party fraud** within `isFraud=1`. Any design requiring that distinction — and Stage 3's decision rule does require it — cannot be validated on this data. See the assumption notice below.
- **There is label noise in the other direction too:** unreported fraud is labelled legitimate, so the ground truth itself contains false negatives. Measured recall is against this label, not against true fraud incidence.

The "linked posterior transactions" rule also clusters card entities across the label, which is why the train/calibration/test split is temporal (earliest 70% / next 10% / final 20% by `TransactionDT`) rather than random — a random split would leak clustered entities across the boundary.

## Known limitations

Stated up front, not in a footnote, because reporting its own limitations is the strongest thing this submission has.

**The unvalidatable inference (`dispute_autopilot.config.ASSUMPTION_NOTICE`).** Quoted verbatim, because it appears unchanged in the README, the demo video, and every `Decision` API payload — it has no default value in `contracts.py`, so a `Decision` literally cannot be constructed without carrying it:

> "Contest recommendations rest on an inference that is not validated by this dataset: a transaction scored as low chargeback risk that is nevertheless charged back is treated as more likely to be first-party misuse. IEEE-CIS cannot separate first-party misuse from third-party fraud, so this is calibrated to published industry base rates, not measured here."

Concretely: Stage 3 uses `(1 - p)` as a win-probability input, on the reasoning that a transaction that looked safe at collection time and still got disputed is disproportionately likely to be friendly fraud. That reasoning is supported by published base rates (first-party misuse is cited at 40–75% of chargebacks, a wide and source-dependent range) but it is an inference, never a measured quantity on this data. If it is wrong for a given merchant's fraud mix, the win-probability model degrades gracefully rather than catastrophically: `lift(p)` is clipped to `[0.5x, 2.5x]` specifically so the unvalidated model score cannot dominate the published base rate it is multiplying.

**The G1 censoring gate.** The 120-day label horizon is shorter than the 183-day span of the data, which raises the possibility that Vesta labelled at a fixed collection date rather than retrospectively — in which case the final ~120 days of the dataset would be under-labelled, and precision measured on a test split drawn from that tail would be understated. This was checked (`eval/gates/g1_censoring.py`) before the split was built, not after metrics were published. Result: head rate (first 30 days) 0.026368, tail rate (last 30 days) 0.035229, ratio 1.336038 — **verdict CLEAN**. The tail rate is higher than the head, the opposite of what censoring would produce, so the full 183-day range was retained (`matured_max_day` unset; `eval/reports/metrics.json` confirms `sample_n: null, matured_max_day: null` — the full dataset, untruncated). The check is one-sided: it cannot rule out a rising true rate masking partial censoring, since the counterfactual (the label each tail transaction would have carried after a full, undisturbed 120-day window) is exactly what's unobservable. See `docs/gates/G1-censoring.md` for the full write-up, including what the test cannot establish.

**The evidence corpus is synthetic.** IEEE-CIS contains no order records, tracking numbers, or support tickets. `src/dispute_autopilot/casefile/synthesize.py` generates them deterministically and consistently with each row's real features (an AVS-match flag in the data produces a matching billing-proof record, a large `dist1` produces a shipping/billing address mismatch) — but the model that scores transactions runs on real labelled data, while the evidence it later argues from is synthetic. Groundedness remains a valid property to check on synthetic sources (it asks whether the assembler invented facts absent from its source, true regardless of the source's provenance), but no claim about representment win rate should be inferred from this corpus.

**Stage 2's benefit is simulated, not measured.** There is no counterfactual in IEEE-CIS for "what would have happened to a chargeback's outcome had evidence been preserved in advance." Every rupee figure attributable to the vault belongs to Family B and is labelled as simulation everywhere it appears.

**What the groundedness verifier does not catch.** Quoted from the module's own docstring, because the README asserts a safety property and the claim must be exact: the verifier checks that every claim names a source key that exists in the case file, and that every *identifier-like token* in the claim (tracking numbers, order references, amounts) also appears in that source's value. That rule catches a plausible-sounding invented tracking number. It does **not** catch invented prose carrying no identifier — a claim like "the customer confirmed receipt by phone" passes verification if it cites a real, existing source key, even if that source never said any such thing. The defence against that failure mode is the system prompt's restriction plus the refusal gate acting on ungrounded *identifier* claims, not this function — and this README does not claim the verifier prevents all fabrication.

**The USD→INR conversion is a stated assumption, not a measurement.** IEEE-CIS is US card data; `TransactionAmt` is in US dollars (the competition host states this explicitly). `config/costs.yaml` fixes `usd_to_inr: 83.0` as a single published constant, chosen so every rupee figure in this README can be divided back out by a reader who disagrees with the rate. There is no Indian ground truth in this dataset — the conversion is necessary to produce rupee figures at all, and it is disclosed as a conversion rather than presented as measured Indian transaction data.

**Two cost inputs are explicitly marked `PLACEHOLDER` in `config/costs.yaml`:** `ops_cost_inr` (₹250, staff time per contested dispute) and the `PASSIVE`/`ACTIVE` posture costs (₹12 / ₹75, storage-and-logging and signature-on-delivery respectively). These were not independently sourced. The contest fee itself (₹750) is not a placeholder in the same sense — Razorpay does not publish a dispute fee at all (its pricing page lists only transaction and refund fees), so ₹750 was set at the top of the most commonly cited India-specific band (₹200–750) deliberately: a higher fee makes contesting look less attractive, which understates the model's simulated benefit rather than inflating it. This is also why the threshold sensitivity sweep and the UI's fee slider exist — they report the decision boundary across the cited range rather than asserting a single number is correct.

**The live Razorpay path is implemented but unexercised.** Gate G2 confirmed that test-mode credentials authenticate and the disputes endpoint responds, but the test-mode dispute collection is empty — a dispute is created when an issuing bank raises a real chargeback against a real settled payment, not something a merchant can conjure on demand in a test account. `LiveClient` exists and passes the same schema validation as `DryRunClient`, but no run of this project has transmitted a contest payload to Razorpay's servers. The demo and every reproduction path here use the dry-run adapter, which constructs and schema-validates the exact `PATCH /v1/disputes/:id/contest` payload without sending it. See `docs/gates/G2-razorpay-test-mode.md`.

## Reproduce every number

```bash
python -m eval.run_eval
```

This single command retrains the model on the temporal split, fits the isotonic calibrator, regenerates `eval/reports/metrics.json` (Family A and Family B, including `pr_curve.png`, `calibration.png`, `threshold_sweep.png`), and prints the same JSON to stdout. There are no manual steps and no numbers typed in by hand anywhere in this README — check any figure above against the regenerated file.

Family C has no reproduction command in this repository yet, because the script does not exist (see above). This is stated rather than glossed over.

## Setup

Requires Python 3.11 or 3.12 (not 3.13 — LightGBM wheel availability), a Kaggle account, and about 8 GB of free disk and RAM.

```bash
git clone <this-repo-url>
cd RazorPay_AI

python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python -m pip install -e .
```

**Kaggle data.** Visit `https://www.kaggle.com/c/ieee-fraud-detection/rules` and click **I Understand and Accept** — the download 403s without this, with an error that does not explain why. Then create an API token (Kaggle → Account → Create New API Token) and save `kaggle.json` to `~/.kaggle/kaggle.json`. Then:

```bash
.venv/Scripts/python -m dispute_autopilot.ingest.download
```

**Environment file.** Copy `.env.example` to `.env`. Razorpay test-mode keys enable the (unexercised, dry-run-only) live-client code path; an `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` enables live evidence assembly. Neither is required — with no key set, `assemble()` falls back automatically to a deterministic template assembler that copies vault values verbatim (grounded by construction, useful for browsing the UI, but not a Family C benchmark; see Known Limitations).

**Regenerate the metrics** (see above):

```bash
.venv/Scripts/python -m eval.run_eval
```

**Run the demo console:**

```bash
.venv/Scripts/python -m streamlit run ui/app.py
```

Three tabs: Triage (score a transaction, watch it produce `CONTEST`/`ACCEPT`/`REVIEW`, and optionally trigger fault injection to watch the refusal gate fire on demand), Metrics (Family A and B, rendered from `eval/reports/metrics.json`), and Economics (the fee slider — the sensitivity sweep, live).

**Run the test suite:**

```bash
.venv/Scripts/python -m pytest -q
```
